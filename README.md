# Асинхронный сервис процессинга платежей

Решение тестового задания из `requirements.pdf`. FastAPI и Pydantic v2, асинхронный SQLAlchemy 2, PostgreSQL, RabbitMQ с FastStream, Alembic и Docker Compose. Платёжный шлюз эмулируется по условию: ожидание 2–5 секунд, 90% успешных платежей и 10% окончательных отказов.

## Запуск

Нужны Docker с Compose v2. Из корня проекта:

```bash
cp .env.example .env
docker compose up --build -d --wait
```

API: `http://localhost:58000`. RabbitMQ Management: `http://localhost:55673`, локальный пользователь `payments`, пароль `payments-local`. Эти демонстрационные значения не являются рабочими секретами. Пароли и ключ задаются через `.env`, который исключён из Git и Docker-контекста. При изменении пароля уже созданной БД или RabbitMQ нужно отдельно обновить пользователя: переменные инициализации действуют на пустые тома.

Compose содержит ровно четыре сервиса: `postgres`, `rabbitmq`, `api`, `consumer`. API применяет миграции перед запуском; consumer запускается после готовности API. Outbox-публикатор работает фоном внутри consumer. Один обработчик выполняет платёж, сохраняет результат и отправляет webhook. Prefetch равен 1; очередь дополнительно использует single active consumer.

Порты можно изменить в `.env`. Все опубликованные порты привязаны к loopback. Логи и остановка:

```bash
docker compose logs -f api consumer
docker compose stop
```

`docker compose down` удаляет контейнеры и сеть, сохраняя данные. `docker compose down -v` также удаляет данные этого проекта — используйте только для намеренного сброса.

## API

Оба эндпоинта требуют `X-API-Key`. Swagger и OpenAPI отключены. Создание дополнительно требует `Idempotency-Key` (1–255 символов, не пустой после удаления пробелов). Сумма положительная, максимум 16 цифр до точки и 2 после неё, хранится как `Decimal`/`NUMERIC(18,2)`. Передавайте сумму строкой. Валюты: RUB, USD, EUR. Описание ограничено 1000 символами; metadata — JSON-объект; webhook_url — URL до 2048 символов. По умолчанию разрешён HTTPS к публичным адресам; локальный HTTP доступен только для явно разрешённых origin.

```bash
curl -i http://localhost:58000/api/v1/payments \
  -H 'X-API-Key: local-demo-api-key' \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"1500.00","currency":"RUB","description":"Оплата заказа","metadata":{"order_id":42},"webhook_url":"http://host.docker.internal:9000/webhook"}'
```

Ответ `202 Accepted`:

```json
{"payment_id":"<UUID>","status":"pending","created_at":"<время UTC>"}
```

Адрес webhook должен быть доступен из контейнера consumer. `host.docker.internal` работает в Docker Desktop. На Linux для локального получателя можно добавить `host-gateway` через собственный Compose override или указать доступный адрес хоста. Получатель должен действительно принимать POST; пример не создаёт его автоматически.

```bash
curl http://localhost:58000/api/v1/payments/<UUID> \
  -H 'X-API-Key: local-demo-api-key'
```

GET возвращает сумму, валюту, описание, metadata, webhook_url, даты, статус и состояние доставки webhook. Неизвестный UUID: `404`; неверный ключ: `401`; некорректный запрос: `422`; слишком большое тело: `413`; неподдерживаемый Content-Type: `415`.

Одинаковый ключ и нормализованное тело возвращают тот же payment_id с текущим статусом и `202`, без нового события. С другим телом ответ — `409 Conflict`. Суммы `1500`, `1500.0`, `1500.00` эквивалентны; порядок ключей JSON не влияет. Текст, значения metadata и адрес webhook входят в сравнение. Ключи хранятся без автоматического удаления.

## Webhook

POST с `Content-Type: application/json` и стабильным `X-Webhook-Id`, равным payment_id:

```json
{
  "payment_id": "<UUID>",
  "status": "succeeded",
  "amount": "1500.00",
  "currency": "RUB",
  "processed_at": "2026-10-08T10:00:00+00:00",
  "metadata": {"order_id": 42}
}
```

Любой HTTP `2xx` означает успешную доставку; redirects не выполняются. Отказ шлюза отправляется с `status=failed`. Таймаут HTTP по умолчанию — 5 секунд; дополнительно ограничено общее время вызова. Ошибки уведомления не меняют статус или время обработки платежа.

Webhook доставляется **at least once**. Если получатель принял запрос, но ответ или фиксация подтверждения потерялись, уведомление может прийти повторно. Получатель должен дедуплицировать его по `X-Webhook-Id`. Настоящее списание денег не выполняется; для подключения реального шлюза необходим его собственный идемпотентный ключ и механизм сверки результата после неопределённого ответа.

## Транзакции, outbox и повторы

- Payment и первое событие outbox создаются одной транзакцией. Уникальное ограничение БД на ключ защищает и от одновременных запросов; используется PostgreSQL `INSERT ... ON CONFLICT` через SQLAlchemy.
- Публикатор выбирает готовые события с `FOR UPDATE SKIP LOCKED`. Публикация идёт через exchange `payments.events`. Сообщения persistent, очереди durable; публикация mandatory, publisher confirms включены, ненайденный маршрут вызывает ошибку. `published_at` сохраняется только после `Basic.Ack` брокера.
- При сбое между подтверждением брокера и commit событие публикуется повторно с тем же event_id. Consumer блокирует событие, затем платёж; `completed_at` исключает повтор завершённого события.
- Результат шлюза фиксируется перед webhook отдельной транзакцией. При повторе consumer проверяет статус и выполняет только недоставленное уведомление.
- **Три попытки — первая и два повтора.** Бюджет общий на обработку события: технические ошибки шлюза и webhook вместе допускают максимум три попытки. Отдельные счётчики этапов нужны для диагностики. Задержки по умолчанию — 2 и 4 секунды, формула `RETRY_BASE_SECONDS * 2^(attempt-1)`.
- Повтор хранится в outbox с `available_at`; старое событие завершается в той же транзакции. Задержки и счётчики переживают перезапуск. Нет очередей задержки, отдельных consumer или дополнительных сервисов.
- 10% отказов эмулятора — окончательный бизнес-результат `failed`, без повторного платежа. Техническая ошибка шлюза повторяется; после третьей платёж становится `failed`, отправляется webhook и создаётся диагностическое событие DLQ. Если бюджет исчерпан на webhook, платёж сохраняет результат, сообщение попадает в DLQ; после предыдущих технических ошибок шлюза на уведомление остаётся меньше попыток.
- `payments.dlq` получает диагностическое событие через outbox и publisher confirm. Некорректные сообщения отклоняются через exchange `payments.dead`, связанный с DLQ. В DLQ нет автоматического consumer: содержимое доступно в RabbitMQ Management, восстановление требует разбора причины.
- ACK исходного сообщения выполняется после commit результата и решения о повторе/DLQ. При ошибке БД сообщение возвращается в очередь с паузой 1 секунда. Недоступность инфраструктуры не расходует попытки шлюза или webhook.

Оба внешних вызова выполняются под блокировкой платежа и ограничены по времени. Это простое решение для одного consumer: оно исключает параллельную обработку, но удерживает соединение БД. Аварийно прерванная незавершённая транзакция откатывается; такой вызов может повториться и не учитывается как завершённая попытка. Настройки рассчитаны на тестовое задание, без дополнительных требований к throughput и высокой доступности. Durable-очереди и тома не заменяют резервное копирование или кластер RabbitMQ.

## Защита и её границы

Авторизация выполняется до чтения тела; ключ сравнивается через `compare_digest`. Дубли критичных заголовков и ключей JSON отклоняются. Лимиты: тело 64 КиБ, заголовки 16 КиБ, вложенность JSON 32 уровня, 4096 узлов; чтение тела ограничено 10 секундами. Нулевые символы, некорректный Unicode и неконечные числа запрещены. API ограничивает число одновременных соединений, контейнеры — память и размер логов.

Webhook проверяется при создании и непосредственно перед доставкой. По умолчанию разрешены публичные HTTPS-адреса на портах 80/443. Все DNS-ответы должны пройти проверку; соединение закрепляется за проверенным IP с исходными Host и TLS SNI. Проверка сертификата включена; redirects, прокси из окружения и перенос cookies между уведомлениями отключены. Тело ответа webhook не читается. API-ключ получателю не передаётся.

`ALLOWED_WEBHOOK_ORIGINS` разрешает строго определённые сочетания схемы, хоста и порта, включая локальные HTTP-получатели. Это доверенная настройка администратора: она открывает доступ к внутреннему адресу и допускает передачу JSON без TLS при схеме HTTP. Даже для таких исключений запрещены link-local адреса, multicast и unspecified. Удалите демонстрационные исключения вне локального запуска.

DSN и API-ключ скрыты в представлении настроек. Ошибки API не содержат исходных данных; параметры SQL и URL webhook не выводятся в штатные логи. Приложение запускается с UID 10001, файловая система контейнеров API/consumer доступна только для чтения, capabilities удалены. Порты опубликованы только на loopback. Роль приложения PostgreSQL не имеет SUPERUSER/CREATEDB/CREATEROLE; администратор использует отдельный пароль. RabbitMQ разрешает только ресурсы `payments.new`, `payments.dlq`, `payments.dead`, `payments.events`; имя узла стабильно при пересоздании контейнера.

Один статический ключ по ТЗ означает одну область доверия: любой обладатель ключа может читать платежи по UUID и создавать их. Транспорт внутри локального Compose не использует TLS; данные и metadata сохраняются в обычном томе без автоматического удаления и шифрования средствами приложения. Для внешнего развёртывания нужны отдельные сильные секреты, HTTPS на входе, контроль доступа к хосту, резервные копии и ограничения трафика. Это условия эксплуатации, дополнительные сервисы в решение не добавлены. Аудит и фактические результаты: [docs/security-audit.md](docs/security-audit.md).

## Тесты

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/). Зависимости закреплены в `uv.lock`. Тесты используют настоящий PostgreSQL и RabbitMQ. PostgreSQL-схема для каждого теста уникальна и удаляется после него; брокер использует отдельный vhost `payments_test`.

```bash
uv sync --frozen
# Сначала создайте .env, если ещё не сделали этого.
docker compose up -d --wait postgres rabbitmq
docker compose exec -T rabbitmq rabbitmqctl add_vhost payments_test
docker compose exec -T rabbitmq rabbitmqctl set_permissions -p payments_test payments '.*' '.*' '.*'
uv run pytest -q
uv run ruff check app tests scripts migrations
uv run ruff format --check app tests scripts migrations
```

Команды создания vhost выполняются один раз. Для своего окружения задайте `TEST_DATABASE_URL` и `TEST_RABBITMQ_URL`; значения по умолчанию соответствуют `.env.example`. Учётная запись тестовой БД должна иметь право создавать схемы. Для запуска тестов вне Compose копирования конфигурации в контейнер не требуется.

Проверяются: API и Decimal, 20 конкурентных запросов, конфликт тела, атомарный откат, дубли сообщений, три попытки и задержки, окончательный отказ шлюза, сохранение результата при сбое webhook, потерянный confirm, восстановление после отмены обработки, persistent-сообщения и настоящая DLQ, некорректные сообщения без блокировки consumer.

Полная проверка живого Compose запускает временный HTTP-получатель на хосте, создаёт демонстрационные платежи, аварийно завершает **только consumer этого проекта** и временно останавливает **его RabbitMQ**:

```bash
docker compose up --build -d --wait
uv run python -m scripts.verify_compose
```

Получатель работает только во время проверки и не добавляется в Compose. На Docker Desktop используется `host.docker.internal:59001`; переменные `VERIFY_WEBHOOK_HOST`, `VERIFY_WEBHOOK_PORT`, `VERIFY_API_URL` позволяют изменить адреса. Management API в проверке использует локальный порт 55673. Не запускайте её против рабочего окружения.

## GitHub Actions

Workflow `.github/workflows/ci.yml` запускается при push в main, pull request и вручную. Он проверяет Ruff, все тесты с настоящими PostgreSQL/RabbitMQ, полный цикл миграций на пустой БД, известные уязвимости runtime-зависимостей, сборку всех образов и аварийные сценарии Compose, включая пересоздание брокера. Каждый запуск использует отдельное временное окружение и демонстрационные значения из `.env.example`; рабочие секреты не нужны. Токен имеет только право чтения репозитория, actions закреплены по SHA. Override `.github/compose.ci.yaml` позволяет Linux runner отправлять webhook получателю на хосте, сохраняя четыре сервиса.

Результат конкретного запуска доступен во вкладке Actions. Успешный CI подтверждает перечисленные проверки этой версии; результат сканирования зависит от актуальной базы известных уязвимостей.

## Структура

`app/api.py` — API и идемпотентность; `models.py` — две таблицы; `processing.py` — этапы обработки и webhook; `publisher.py` — публикация outbox; `worker.py` — единственный consumer и топология RabbitMQ. `migrations/` содержит начальную миграцию. `tests/` и `scripts/verify_compose.py` содержат воспроизводимые проверки. `scripts/verify_broker_recreation.py` проверяет сохранность очереди при пересоздании брокера (временно останавливает consumer этого проекта). `docs/verification.md` фиксирует фактически выполненные проверки и их границы.
