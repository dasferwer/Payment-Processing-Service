# План реализации процессинга платежей

Исполнение: последовательно в текущей сессии, по прямому указанию пользователя «Начинай писать код».
Цель: законченное решение по requirements.pdf.
Спецификация: ../specs/2026-10-08-payments-design.md.
Стек: FastAPI, Pydantic v2, async SQLAlchemy 2, PostgreSQL, RabbitMQ/FastStream, Alembic, Docker Compose.

1. API и хранение: app/config.py, db.py, models.py, schemas.py, api.py; миграция; tests/test_api.py. Сначала проверки 202/401/404/409/422, Decimal, одного payment/outbox при 20 запросах и отката при ошибке outbox; затем реализация и полный pytest.
2. Consumer и outbox: app/processing.py, publisher.py, worker.py; tests/test_processing.py. Сначала проверки сохранения результата, трёх попыток, задержек, дублей, восстановления и DLQ; затем реализация и полный pytest. Интерфейсы: Processor.handle(event_id), Publisher.publish_batch(); зависимости — sessionmaker, gateway, webhook и broker.
3. Окружение: Dockerfile, compose.yaml, .env.example, uv.lock, README.md; tests/test_broker.py и scripts/verify_compose.py. Проверить настоящий брокер, publisher confirms, повторную доставку и Compose. Зафиксировать команды, результаты и ограничения.
4. Финальное ревью: транзакции, блокировки, deadlock, подтверждения, crash windows, таймауты, корректность retry, чистота русского текста. Исправления проверять регрессионными тестами.

Особое внимание: эквивалентные Decimal/JSON; потерянный publisher confirm; сбой после сохранения платежа; успешный webhook без сохранения подтверждения; недоступность инфраструктуры. Инфраструктурная недоступность не считается отказом платежа: сообщение остаётся неподтверждённым и возвращается в очередь.
